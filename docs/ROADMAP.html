Notion Harness Twelve Month Roadmap

Eight pillars, decimal-numbered so any node can be expanded in place. Hermes is the only engine. The UI is the product. Everything below assumes both.

Preamble

The one-sentence strategy

Hermes solves the harness. You solve the interface. The product is a document workspace where agents are teammates, not a chat window with a task list bolted on.

Every scope decision below resolves against that sentence. When something is ambiguous, ask: does this make Hermes usable by someone who would never open a terminal? If no, it waits.

1Month 0–1 · v0.1

Foundation

Two weeks of work that make the next eleven months possible. None of it is a feature; all of it is load-bearing.

1.12 days

Version control

git init in notionharness. It has none. You are about to build per-project git worktrees and hand agents write access to a codebase with no undo. First commit, .gitignore for .next/node_modules/.env/.sandbox-workspaces, then a branch protection habit: agents work on branches, you merge.

1.21 day

Documentary truth

You currently have three roadmaps written against dead assumptions and one handoff that is factually wrong. Any agent reading them makes bad decisions with total confidence.

  • Delete HANDOFF.md — it claims TASK-7 is untouched; there are 57 files and a working 531-line DataSource.
  • Archive ROADMAP_TEAMOS.md and assistanceu/ROADMAP.md under docs/archive/ with a header saying superseded.
  • Rewrite AGENTS.md to carry D1–D13, the Payload/raw-pg boundary, the "never paste Multica UI source" rule, and the surviving environment gotchas (Docker named volumes need a restart on dependency change; DATABASE_URI points at hosted Supabase, not the local container; server code uses the Local API with overrideAccess, never Payload REST).
1.31 day

One data plane

TeamOS sits on one Supabase project, notionforge on another. Consolidate onto one Postgres now, while there is nothing to migrate. Confirm push: false stays — migrations are the source of truth and Payload's dev-mode auto-push will otherwise offer to drop Better Auth's tables.

1.41 day, decision only

Deployment shape

Long-lived SSE and WebSocket connections do not survive serverless. Decide once, now, because it constrains Pillar 4: either self-host Next on a Node process, or keep Next wherever you like and split the realtime hub into its own small Node service. Recommendation: separate realtime hub. It keeps the web app deployable anywhere, isolates the one process that must hold thousands of open sockets, and lets you scale or restart it without touching the app.

1.54 days

UI foundation

components/ui/ currently holds one file. You are picking a base layer whether you decide to or not, so decide: install shadcn/Radix, define the token layer (color, type scale, spacing, radius, elevation) once, wire light/dark at the token level, and set the density. Everything in Pillars 2 and 5 is built on this — retrofitting a design system across sixty components is a month you will not get back.

Take shadcn's June 2026 chat primitives (MessageScroller, Message, Bubble, Attachment, Marker) at the same time; MessageScroller alone handles anchored turns, streamed replies, saved-thread restore and prepended history, which is the scroll behaviour everyone gets wrong.

2Month 1–3 · v0.2

Workspace core

The Notion base, finished and dogfooded, with zero agents. If this is not already a better place to track work than what you use today, agents will not rescue it.

2.11.5 weeks

System tables — Payload collections

workspaces (with task_prefix + task_counter), members, projects, tasks, task_statuses, task_links, followers, comments, activity, notifications, artifacts. Migrations, generated types, access control, admin panel.

Three details that are cheap now and structural later: position float for fractional drag-ordering; revision bigint for optimistic concurrency; last_activity_at denormalised so board sorting never joins.

2.23 days

Status catalogue

Workspaces define their own statuses, but every one carries a category that is one of seven fixed values — backlog, todo, in progress, in review, done, blocked, cancelled. Board grouping, automation and the broker read category; only the UI reads the name. This is how you get custom workflow without every consumer having to handle an unknown string, and it is genuinely impossible to retrofit.

2.31 week

The DataSource layer

One interface, three implementations, one renderer. PayloadDataSource (system tables) and UserDatabaseDataSource (generic databases + database_rows with cells jsonb) are new; TeableDataSource already exists and becomes optional. The block takes a source prop.

This is what makes "the task grid looks like my editor" true by construction rather than by imitation — it is literally the same component. Per D4, affine:database is never used for anything queryable.

2.41 week

Editor hardening

You are on BlockSuite 0.19.5 internals with a hand-rolled Markdown serializer, because no public adapter is exported. That is a standing liability: any new block flavour is silently skipped on export.

  • Pin BlockSuite exactly; no caret ranges.
  • Every touchpoint behind lib/blocksuite-*, nothing importing BlockSuite directly from a component.
  • A case per database flavour in serializeChildren/markdownToDoc.
  • A round-trip test per block flavour in CI. Export → import → export must be byte-identical.
2.51.5 weeks

Task and project surfaces

Board (dnd-kit, paginated per column), list (virtualised, grouped), table (TanStack Table headless + virtual). Saved views with named scopes and a baseline diff so unsaved changes are visible. Filter chips, column picker. The side drawer with Overview / Activity / Sessions tabs — Sessions is empty until Pillar 4, and that is fine.

2.61 week

Activity spine, follows, notifications

One polymorphic activity table behind every Activity tab in the product — task, project, page, later run. Creator auto-follows on create; follows drive notifications. Getting this as one table is what makes "every entity has a timeline" a week of work instead of a rewrite per entity, and it is your audit log when you sell this.

2.71 week

Dogfood

3Month 3–5 · v0.3

The Hermes seam

Two surfaces, one boundary. Confusing the execution path with the control plane is the mistake that costs a week.

3.12 days

The RunEvent contract

type RunEvent =
  | { type:'message',    role, text }
  | { type:'thought',    text }
  | { type:'tool_call',  id, name, input, status }
  | { type:'tool_result',id, output, isError }
  | { type:'permission', id, title, detail, options }
  | { type:'file_change',path, diff }
  | { type:'terminal',   id, chunk }
  | { type:'usage',      provider, model, tokens, costTicks }
  | { type:'session',    externalId }   // pin immediately
  | { type:'done',       status:'ok'|'error'|'cancelled' }

Every event carries a monotonic seq assigned by the daemon. Ordering comes from seq, never from timestamps or insertion order — batched inserts return unordered and this is the bug that silently scrambles transcripts.

Per D6 this boundary stays even though Hermes is the only engine. It is not hedging, it is keeping the UI from being welded to a wire format you do not own.

3.22 weeks

ACP execution adapter

hermes acp over stdio via @agentclientprotocol/sdk. initialize → session/new (or session/resume) → session/prompt, normalised to RunEvent.

  • Pin the session id the instant it appears, before the run can crash. This single line is the difference between a system that resumes and one that starts over.
  • Serve terminal/* for the agent's own shell calls — bounded tail buffer, rune-safe truncation, kill waits for the whole process group.
  • Handle session/request_permission as a real blocking request that reaches a human (Pillar 5.4), with a timeout that denies once rather than cancelling the turn.
  • MCP servers travel inside the session protocol (session/new's mcpServers, resent on session/resume) — never written into the runtime's own config file.
  • Distinguish permanent resume rejection from transient failure. A resume that silently lands on a fresh thread must inject a continuity notice, not pretend nothing happened.
3.32 weeks

Hermes control plane

Everything ACP does not carry, and this is where your product value concentrates: profiles, skills, MCP servers, models and providers, cron, memory, session lists. You proxy Hermes's HTTP API and put a real interface on it. hermes-webui's api/profiles.py (~2,500 lines), api/config.py and api/models.py are your specification — they encode years of edge cases you would otherwise rediscover.

Do not reimplement any of it. Proxy, and own the UI.

3.41 week

Per-agent identity

D2 in practice. Each agent gets its own Hermes profile. Per run, build a HERMES_HOME overlay so the agent sees only its own skills — but symlink memories/ out to a persistent per-agent store and state.db out to a per-conversation store, so memory and transcript survive while the task directory is disposable. Shard sessions per conversation, not per agent: tasks in one conversation run serially, so a shard has one writer, and two tasks never share a SQLite file.

Known and accepted limitation: two concurrent runs of the same agent are last-writer-wins on memory, because Hermes rewrites those files whole. Surface it in the UI rather than pretending otherwise.

3.51 week

Agents and runtime profiles

runtime_profiles (protocol_family, command_name, fixed_args, enabled) separate from runtimes (a registered instance on a host). Profile says what it speaks; runtime says where it is and whether it is up. That separation is what makes an in-house Hermes fork with a different binary name work without a code change — and it is what makes your runtimes list meaningful.

Plus the agents collection: model, thinking level, instructions, custom_env, custom_args, mcp_config, skills, max_concurrent_runs, permission mode. And the agent editor UI, which is the first screen that makes Hermes usable by a non-developer.

Gate 3From a Node script, start a Hermes run, stream normalised RunEvents, answer a permission request, and resume the session on a second turn.
4Month 3–5 · v0.3

Runtime and daemon

The instant-feeling half. Built concurrently with Pillar 3 — they are two ends of the same wire.

4.11 week

Daemon skeleton

Node, single binary via pkg or a bundled runtime. harness daemon start, per-profile state dir, pidfile, log file, health endpoint, foreground mode for launchd/systemd/Windows Service. Probes for hermes on PATH at startup and re-probes on binary change. Registers each detected runtime with the server; deregisters on shutdown with a structured reason so the UI can say why a runtime went offline, not just that it did.

4.21 week

Outbound control channel

One WebSocket, daemon → server. Never the server dialling in. Works behind NAT and CGNAT with no port forwarding, no tunnel, no firewall rule. Work goes down it, events come up it, heartbeats every 15s. HTTP fallback for terminal reporting with a retry schedule, because a lost completion is the one message you cannot drop.

One subtlety worth stealing: if a claim frame is sent but the socket dies before the response arrives, the outcome is uncertain — do not retry over HTTP, or you double-claim. Wait, and let the lease sweeper resolve it.

4.31.5 weeks

The broker

Raw pg per D5. Roughly 800 lines and the only genuinely novel engineering in the plan.

  ENQUEUE  INSERT runs {queued, attempt:1}
           blocked by a partial unique index: at most one
           non-terminal run per (task, agent)

  CLAIM    UPDATE runs SET status='dispatched',
             lease_expires_at = now() + 60s
           WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED
                       ORDER BY priority DESC, created_at ASC)
           RETURNING *
           refuse if another run for the same (task, agent) is
           dispatched | running | waiting_directory

  SETTLE   complete | fail | cancel, with retry on the terminal POST
           retryable failure + attempt < max → new run, retry_of set,
           attribution inherited
           wipe mcp_overlay, revoke run token

  RECOVER  sweeper re-queues runs stuck 'dispatched' with
           started_at IS NULL and an expired lease — the claim
           committed but the response never got home

Never select-then-update. Two hosts will both win.

4.41.5 weeks

Working copies

Per repo per host: one bare clone as a shared object store; per run a git worktree add -b agent/<agent-slug>/<run-id> off it, so a run's .git is a pointer file rather than a copy. Re-derive the remote default branch with git remote set-head origin --auto so an upstream master→main rename doesn't pin you forever. Eviction is always safe — worst case the next run re-clones.

Local directories are the sharp edge: in_place guarded by a per-path mutex with a real waiting_directory run status surfaced in the UI, or worktree which skips the mutex because isolation is the point. Without this, two agents corrupt the same checkout and you will not immediately understand why.

Garbage collection with explicit TTLs, and never touching a directory a running task holds.

4.51 week

The hot path — direct browser ↔ daemon

The differentiator. When browser and runtime are the same machine or the same Tailnet, the browser opens a second WebSocket straight to the daemon and tokens never touch your server. Sub-millisecond. Server-relayed is the automatic fallback when they are not co-located.

Persist-then-broadcast on both paths: push immediately to any connected browser (fast, dropping a frame is fine), batch-write to the server every ~150ms (durable, ordered). Client merges by seq and REST-backfills on reconnect. The fast path is allowed to be lossy precisely because the durable path heals it.

Multica and Devin are cloud-first and structurally cannot do this. Build it in this pillar, not later — it is much harder to retrofit than to design in.

4.61 week

Terminals

node-pty + xterm.js on a dedicated socket carrying raw bytes, never JSON-wrapped. Windows works via ConPTY — which is exactly what hermes-webui's Python terminal cannot do (api/terminal.py is Unix-only), and you develop on Windows.

Keep the distinction sharp: the agent's own shell calls arrive as ACP terminal/* run events; a human terminal on a runtime is a separate channel with a separate lifecycle and separate authorization.

4.71 week

Security posture

  • Run tokens. A short-lived credential scoped to one (run, agent, workspace, user), minted at claim, dead at settle. The agent never holds a workspace credential — which matters enormously once it can create and assign tasks through your MCP server.
  • Two attribution columns. originator_user answers "whose authority" and is used only for authz. accountable_user answers "whose budget and audit trail" and is never consulted for authz. Collapsing them makes a delegated agent either over-privileged or unbillable.
  • Permission mode is an explicit product choice. Bypass-everything is defensible for a trusted local agent and indefensible as a default. Make it a per-agent setting with a visible posture, and never claim isolation you are not enforcing — lib/sandbox/config.ts silently falls back from gVisor to runc, which on your machine is always.
  • Per-run MCP overlay wiped on terminal status, so a live bearer token never lingers in a settled row.

5Month 5–7 · v0.5

The agentic interface

Where the product stops being infrastructure. Budget more time here than on the daemon — this is where "instant" is actually won or lost.

5.12 weeks

Re-seat @digitech/hermes-chat

The package is v0.3.0 and real — a working <HermesChat/>, four route handlers, a copilot picker, a history sidebar, two embed surfaces. Its brain is the TeamOS control plane, which no longer exists, so its Phase 6 (HermesBackendAdapter) moves from v0.7.0 to first.

Do it in one pass with D8: drop AI SDK from the streaming path. AI SDK's wire format is token-shaped; ACP events are structurally richer, and flattening tool_call, permission and file_change into text parts destroys exactly what the Tool UI needs. assistant-ui supports "your own server" as a runtime — go RunEvent → assistant-ui runtime directly.

Also retire the package's Phase 10 TipTap workspace editor. You have BlockSuite; do not build a second editor.

5.21 week

One Thread, three chromes

Build the thread once, mount it three ways: a drawer tab on any entity, a full page with a session-list rail, and a lane in the team view. Same component, same data, same adapter. The universal failure mode in this category is shipping "sidebar chat" and "full chat" as separate code and watching them diverge inside a month.

Deliberately not a BlockSuite block. A chat block would put the transcript inside the CRDT, break export and search, and make streaming-while-typing a merge nightmare.

5.31.5 weeks

Tool UI catalogue

A React component per tool kind, registered by name. Bash renders as a terminal card with exit status. Edit/Write render as a diff with syntax highlighting. Read/Grep collapse into a compact "looked at 7 files" row. Everything unrecognised falls back to structured JSON, never a wall of text.

This is the single highest-leverage visual work in the product. It is the difference between a transcript that reads like a colleague's summary and one that reads like a log file.

5.41 week

Approvals as first-class objects

Everyone renders a permission request as a blocking modal in the tab where the run started — which means the agent stalls for six hours the moment you close the laptop. Make an approval an object: an inbox item, an inline thread card, a push notification, answerable from a phone.

This is what converts "agents work while I'm away" from a claim into a fact. Rendering approvals well is worth more than any three other features in this pillar.

5.51.5 weeks

The Inbox is the home screen

With six agents running, a board is stale the second you look at it. What you need is what needs me: permission requests, failed runs, review-ready diffs, questions, mentions. Linear has an inbox. Nobody has an inbox whose items are agent interrupts.

This is the screen you would open thirty times a day, which makes it the product. Build it before the board gets any more polish.

5.61.5 weeks

The transcript pipeline

Four pure passes over the event array, and the reason a 163-step run stays readable:

  1. Timeline — sort by seq, coalesce adjacent text fragments, redact secrets.
  2. Steps — pair each tool_call with its tool_result into one step with a duration.
  3. Groups — fold three-plus consecutive same-tool calls into one row, but never shell commands.
  4. Lanes and outcome — a two-lane tool-vs-thinking timeline bar, and the header chips: "11 files +593 −12", "74 commands", "$4.38".

Plus a filter by tool kind, a search box, and a step inspector panel.

5.71 week

Render performance

The naive client re-renders the whole message list per token and feels worse at four agents than a good one does at twenty. Non-negotiables: batch cache writes on a ~50ms flush rather than per event; merge by seq; virtualise every list; and gate materialisation on whether a mounted component actually observes that run, so a workspace-wide broadcast does not build transcripts nobody is watching.

Measure it. A frame budget and a scripted 8-agent load test, in CI.

5.84 days

Cost and presence

Cost on the card, not just in the modal. "$4.38 · 18m · 163 steps" on a task card is information no project management tool on earth can show. Rollups per project, per agent, per week.

Agent presence. Notion shows human cursors; show agent cursors. An agent touching a block appears as a live avatar on it. You already stream file_change, so it is nearly free — and it is the single detail that flips the feel from job queue to shared space.

Gate 5Five people outside your org run real work through it for two weeks and keep going. Approvals get answered from phones.
6Month 7–9 · v0.8

The moat

The half nobody else can build quickly, because it needs a block editor and a harness in one application. This is the demo that raises money.

6.12.5 weeks

Agents write into the page

Everywhere else the transcript is exhaust — you skim it and close it. Here the agent streams blocks into the task's document as it works: a plan block, then findings, then a summary, then a diff card. The page is the deliverable; the transcript is the audit trail hanging off it.

Mechanically: the run holds a scoped write handle to a block subtree, appends through the same Yjs path a human edit takes, and never touches blocks outside its subtree. After the run there is something worth keeping — which is the problem no agentic tool has solved.

6.22 weeks

Block-anchored threads

The unit of work is not the task, it is a run scoped to a block selection. Select three paragraphs of a spec → "have Mika implement this" → a run whose input is those blocks, whose thread hangs off them like a Notion comment, whose output writes back adjacent.

Notion comments + inline chat + a real harness. It does not exist anywhere, and it is the reason the block editor was worth building in the first place.

6.31 week

Mentions and run cards as blocks

Two things that are legitimately blocks: an @agent mention, and a run card — a lightweight embed that references a run by id and renders its live status, outcome chips and cost inline. Reference, never container. Both need a case in the Markdown serializer per 2.4.

6.42 weeks

Review surface

Per-run diffs with file tree, side-by-side and inline modes, comment-on-a-line, approve-and-merge, request-changes-which-becomes-a-follow-up-run. Branch and worktree state visible. This is where the loop closes and a run becomes shipped work rather than a suggestion.

6.51.5 weeks

Plan / Work / Review modes

Not view tabs — product modes with different affordances. Plan is the doc editor with an agent that argues with you. Work is the inbox plus the board. Review is diffs, approvals and cost. Most tools jam all three into one screen and each is mediocre; separating them lets each be excellent, and it matches how the work actually goes.

Gate 6A spec written in the editor, implemented by an agent that wrote its results back into the same page, reviewed and merged — without leaving the app.
7Month 8–10 · v0.8

Teams and orchestration

Your stated USP, built as data and tools rather than as an engine. There is no scheduler anywhere in this pillar.

7.11 week

Teams with a leader

Three columns: teams.leader, tasks.assignee_type='team', runs.is_leader_run. Assigning work to a team creates a run for the leader. delegated_from_run records lineage. That is the entire orchestration model.

7.21.5 weeks

Delegation through your own MCP server

Extend scripts/notionforge-mcp.ts with create_task, assign_task, update_status, comment, list_project_tasks, read_page, write_blocks. Give the leader that server, scoped by its run token per 4.7.

Delegation becomes something the leader does, through the same API a human uses, written to the same activity table. Every step is visible and auditable, and there is no orchestrator to debug or explain.

7.32 weeks

Leader thread with worker lanes

Four streams of tokens is unreadable at four agents and impossible at eight. Instead: the leader's narration is the main thread, and each worker is a one-line lane — avatar, current tool, elapsed, last action — expanding on click. CI pipeline crossed with a chat.

Readable at eight agents, and it makes the leader's reasoning the story instead of the noise. Keep a 2×2 pane grid as an optional "wall" mode, because it demos well — but the lanes are what people will actually use.

7.41.5 weeks

Triggers and schedules

An automation that creates a task and enqueues a run, from a schedule, a webhook, or a workspace event. Hermes already has per-profile cron and gateway channels — proxy them, do not rebuild them. Runs created this way carry accountable_user = rule owner and no originator, which is exactly the case the two-column attribution model in 4.7 exists to handle.

Gate 7A leader agent splits one request into four tasks, assigns them across two runtimes, and you follow all four from one readable screen.
8Month 9–12 · v1.0

Product readiness

The gap between a thing that works for you and a thing a stranger can install, configure, trust and pay for.

8.12 weeks

Install and onboarding

One command to a working install: Docker compose for the server, a signed daemon installer per platform, a pairing flow that does not involve pasting tokens. First-run wizard: create workspace → install or detect Hermes → create your first agent → run a starter task. Someone who has never used a terminal must reach a completed agent run.

This is the single biggest determinant of whether the product has users, and it is routinely under-budgeted. Two weeks is the floor.

8.22 weeks

Configuration surface

Everything Hermes exposes, with a real interface: agents, runtimes and profiles, models and providers with auth, MCP servers as a workspace library bound per-agent with an explicit enable toggle, skills with files, permission modes, cron. This is the product — it is the entirety of "bring Hermes to people who would never open a terminal."

8.31.5 weeks

Multi-tenancy and roles

Postgres RLS keyed on workspace, roles (owner/admin/member), invitations, share links, per-agent visibility and invocation permissions. Audit log built on the activity table you already have. Do this before the first paying customer, not after.

8.41.5 weeks

Cost control and observability

Usage rollups (hourly and daily, idempotent, with a dirty-queue so cascade deletes are not missed by a plain watermark). Per-workspace and per-agent spend caps with a fail-closed option. Health dashboard: runtimes up, runs in flight, queue depth, error rates, slow claims. Your own logs, viewable in-app rather than over SSH.

8.52.5 weeks

Plugin surface

A zip with a manifest declaring scopes, typed config, UI surfaces, hooks (HTTP or remote-MCP, triggerable by agent / human / UI / event) and bundled skills.

Security model, copied in shape from the best one in open source: the plugin UI runs in an inner iframe with sandbox="allow-scripts" and no allow-same-origin — opaque origin, no cookies, no direct network. It talks to the host over a MessageChannel where identity comes from which private port the message arrived on, because origin is "null" and unusable. The host makes the real API call on the signed-in user's own session, so a plugin can never exceed what that user could do.

8.62 weeks

Desktop app

Electron shell around the same React app, whose real job is managing the local daemon: spawn it, health-poll it, restart with backoff, tail its log into the UI, negotiate version upgrades, pick local directories natively. Also the single easiest install story, which loops back to 8.1.

8.71.5 weeks

Mobile, approvals-first

Not a port. Three screens: inbox, approve/deny, and a readable run summary. Push notifications for permission requests and completions. Shares the data layer, reimplements the views natively.

The value is precise: it is what makes "agents work while I'm away" true, and it is the feature people will describe to other people.

8.81 week

Licensing and packaging

Pick the licence deliberately. Multica's shape — Apache-2.0 plus a no-hosted-service condition plus UI branding — is a reasonable template for open-core with a commercial path, and you have read the actual text. Decide free vs paid tiers, seat model, and whether self-host is unlimited. Ship docs that are honest about what is unfinished.

The five things most likely to go wrong

  1. BlockSuite 0.19.5 internals shift under you. Mitigated by exact pinning, the wrapper module, and per-flavour round-trip tests — all in 2.4. Do not skip the tests.
  2. Pillar 2 gets skipped in excitement. Building the harness onto a mediocre workspace produces a mediocre product with impressive plumbing. Gate 2 is a real gate.
  3. Render performance discovered too late. 5.7 is scheduled, but the load test should exist from Gate 3+4 onward, not from month seven.
  4. Hermes upstream changes its ACP surface. You are single-vendor by choice. Pin the Hermes version you certify against, track its changelog deliberately, and keep the smoke test from Gate 3 in CI against a real binary.
  5. Scope creep from your own roadmap. This document has 44 nodes. Expand nodes into 1.1.1 form as you reach them — never before, or you will plan month nine in month one and be wrong about all of it.
