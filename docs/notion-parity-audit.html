Notion Feature Parity — Gap Analysis

A grounded comparison of NotionForge's current capabilities against real Notion, sourced from Notion's official API reference (property-object, page, block, database) and direct reads of this codebase — not assumed from memory.

Scope: Property types, page model, views, block/content types, platform features Method: Live API docs + live BlockSuite schema reads + live code reads
Bottom line: the single most consequential gap is that database rows aren't real pages yet (§2) — everything else is either already shipped, actively in flight, or a bounded, well-scoped addition. One genuine bug was also found and independently fixed: silent data loss on markdown export for stock block types (§5).

2 "Database Rows Are Pages" — the big architectural gap

The single most consequential finding in this audit.

Confirmed directly from Notion's /reference/page and /reference/block docs: a database row is fundamentally a page inside a database — a complete page entity that can contain any block types as content, independently of its structured property columns. Every Notion page also carries its own icon, cover, properties, and separately-fetched block content.

NotionForge's record-detail-popover.tsx is, today, purely a property-editing modal: a fixed-position dialog with a title derived from the row's Name field (not editable as a real title) and one field editor per Teable field. No icon, no cover, no rich-content body, no own URL — closing it just closes the modal. There's nowhere else to navigate.

What closing this gap concretely requires

  • A database row becomes addressable as its own page — a real route, e.g. reusing the existing /workspace/[slug]/p/[pageId] pattern or a new /workspace/[slug]/row/[teableTableId]/[recordId].
  • An actual content body — either each Teable record gets a paired pages row (via parentPage or a new teableRecordId link) carrying its own docState/BlockSuite doc, or some other doc-per-row storage scheme.
  • Icon/cover need a home — Teable's attachment type could hold a cover field per table; "icon" has no Teable equivalent at all and would need a NotionForge-side convention.
  • The popover UI itself likely needs to become a full-screen/routed page view with a real editor mounted, not a small modal.

P0 Nothing else in this audit approaches "feels like Notion" without this.

3 Nested Pages

collections/Pages.ts already has a self-referential parentPage relationship, explicitly documented as "Parent page for infinite nesting; empty for a top-level page."

Already works today at the regular-page level — this is not a gap.

Database rows nesting sub-pages, however, is confirmed not supported: a Teable record has no relationship to the pages collection right now. This is the same root cause as §2 — once a row becomes a real page, nested sub-pages fall out for free from the existing parentPage mechanism.

P0 Same fix as §2.

Confirmed genuinely missing

Not present in AffineSchemas at all — would need real new BlockSuite blocks, the same class of work as building the Teable block was:

  • Toggle lists, callouts — very common in real Notion docs. P1
  • Column / layout blocks, table-of-contents, breadcrumb P2

Separate finding — a real bug, not a missing feature (now fixed)

The markdown-export serializer originally only had cases for paragraph / list / code / divider / the Teable block — every other insertable block type (image, bookmark, attachment, embeds, latex, frame) silently vanished on export with zero warning. This has since been fixed: every block type now produces either real content or a visible placeholder, and the fallback case is a code-level guarantee — proven unreachable for any block BlockSuite's own model layer will actually let you insert.

Worth noting as a win: Notion's child_database (an inline database block) maps directly to what NotionForge's Teable database block already is — effectively already at conceptual parity.
