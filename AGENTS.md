# NotionForge — durable agent rules

Everything below this line is hand-maintained and never touched by `next dev`. `docs/ROADMAP.html` is the source of truth for product direction and sequencing; this file is the source of truth for the locked decisions and environment facts that constrain *how* code gets written here, regardless of which roadmap pillar you're working. `HANDOFF.md` is a point-in-time status snapshot (what's actually built, dated) — read it for current feature state, read this file for the rules that outlive any one snapshot.

## Locked decisions (D1–D13)

These are settled — don't re-litigate them in a PR or a plan. Full rationale is in `docs/ROADMAP.html`'s preamble table; the ones below have direct, present-day implications for code in this repo. The rest (D2, D6–D10, D13) describe the Hermes/agentic-UI architecture for later pillars and aren't yet load-bearing on anything in this repo today, but don't design around assumptions that contradict them.

- **D3** — Teable is an optional `DataSource`, not a hard dependency. `TEABLE_*` env vars unset must be a supported state once the generic `DataSource` layer (Pillar 2.3) lands — don't add new code that assumes a Teable connection always exists.
- **D4** — `affine:database` (BlockSuite's own stock database block) never holds system or user-queryable data. Generic tabular data goes through `databases` + `database_rows` (Pillar 2.3) or Teable — never the stock block, at any layer.
- **D5** — Payload owns workspace tables (`users`, `workspaces`, `pages`, `teable-databases`, and everything like them). Raw `pg` will own `runs` / `run_messages` / `run_usage` once the Pillar 4 broker lands — those tables need `SELECT ... FOR UPDATE SKIP LOCKED`-style claim semantics Payload's ORM doesn't expose, so when they arrive, don't route them through a Payload collection.
- **D11** — Multica is a reference for ideas only, never source. It's Apache-2.0 plus a no-hosted-service clause plus a UI-branding rider — copying its actual code into this repo (even a small helper) creates real licensing exposure. Read it, don't paste it.
- **D12** — P0 hygiene is done: git is initialized, pushed to `github.com/Digigit24/notionharness`, and pillar work happens on `roadmap/*` branches via worktrees (confirmed: `roadmap/foundation`, `roadmap/datasource`, `roadmap/editor-hardening`, `roadmap/hermes-acp`, `roadmap/ui-foundation` all exist as of this writing). Keep working this way — branch per pillar/node, merge to `main` deliberately, don't commit directly to `main`.

## Payload vs. raw `pg` boundary

Everything under `collections/*` goes through Payload's Local API (`getPayloadClient()` + `payload.find/create/update/delete`, always with `overrideAccess: true` — see the environment gotchas below for why). Never call Payload's REST or GraphQL endpoints from server code; the Local API is faster, type-safe against `payload-types.ts`, and is the only pattern used anywhere in this codebase today. If you ever need raw SQL against tables Payload doesn't own (the future `runs`/`run_messages`/`run_usage` per D5, or a one-off diagnostic read), open your own short-lived `pg.Pool` — see the shared-Supabase note below for why "short-lived and small" matters here specifically.

## Environment gotchas (verified against the live container and repo, not guessed)

- **Production build only, no hot reload.** Container `notionforge-app`, port 3000, entrypoint runs `npm install && npm run build && npm run start` on every start (confirmed via `docker inspect`). Source edits do not hot-reload — after any change, `docker restart notionforge-app` and wait ~1–2 minutes for the rebuild.
- **`node_modules` and `.next` are named Docker volumes, not part of the bind mount.** Confirmed via `docker inspect notionforge-app`: `notionforge-node-modules` → `/app/node_modules`, `notionforge-next-cache` → `/app/.next`; only the repo itself is bind-mounted to `/app`. A `npm install` on the host does not reach the container — the entrypoint's own `npm install` (which already runs on every restart) is what syncs a new dependency into the container's volume, so the standard "restart after any change" rule already covers dependency changes too; there's no separate step needed. If a rebuild ever crashes with a no-stack-trace error right after "Creating an optimized production build," suspect a stale `.next` volume first: `docker exec notionforge-app sh -c "rm -rf /app/.next/*"`, then restart.
- **`DATABASE_URI` points at a hosted Supabase project, not a local Postgres container** (confirmed — Pillar 1.3 will consolidate this onto one Postgres, not done yet). It's a small-tier instance with a real session-mode connection cap (~15, hit and confirmed live this session). Every teammate's dev server and every one-off script competes for that same small pool — keep any `pg.Pool` you open yourself small (`max: 2–3`) and close/let it exit promptly; don't leave an extra dev server idle-running longer than you need it.
- **DB safety rule**: never run a standalone script that calls `getPayloadClient()` against this shared DB. `payload.config.ts` has `push: false` (confirmed present) specifically to stop Payload's dev-mode schema-drift auto-push from silently dropping tables it doesn't recognize — this has already happened once this session to Better Auth's own `user`/`session`/`account`/`verification` tables, which live in the same Postgres database but outside Payload's schema awareness. Verify through the already-running container's Payload client instead of a fresh script. If a script genuinely needs its own Payload client, confirm schema is fully migrated first so there's no drift left for it to prompt about.
- **Teable networking**: self-hosted, separate `teable-selfhost` Docker stack, headless data engine only — its own web UI is never shown to end users. From *inside* `notionforge-app`, reach it via `http://host.docker.internal:3100`, not `http://localhost:3100` (container-vs-host networking; `localhost` inside the container means the container itself). Two separate API keys in `.env` (both confirmed present): `TEABLE_API_KEY` (narrow — day-to-day field/record CRUD) and `TEABLE_API_KEY_CREATOR` (broader — table/base creation only). Deliberately separate scopes; don't merge them into one key.
- **`tsc --noEmit` + `eslint` clean does not guarantee `npm run build` succeeds.** Next.js's SWC bundler is stricter than `tsc` for some syntax (this cost a real incident this session — a build-breaking syntax error passed both checks and looped the container's `unless-stopped` restart policy on a failing build for several minutes before being traced). Always run a real `npm run build` before calling a task done, not just the faster checks.
- **No browser access exists anywhere on this team.** Verification is API/DB/source-level: `curl` against live routes on the container, direct SQL reads via a short-lived `pg` connection, static code reading, isolated Node/`tsx` scripts for anything that needs real execution (e.g. a `happy-dom`-shimmed DOM for BlockSuite mount logic). Flag any pixel-level or visual-alignment claim as unconfirmed rather than asserting it looks right.

## The CSS-cascade-layers / BlockSuite global-CSS gotcha

BlockSuite's Lit components are deliberately "shadowless" (no shadow root, for editor performance) — their `static styles` get injected as **unlayered, unscoped** global `<style>` tags into `document.head`, not scoped to the component. Per the CSS cascade-layers spec, *any* unlayered rule beats *any* layered rule, regardless of specificity — and this app's own Tailwind utilities live inside Tailwind v4's `@layer utilities`. So a bare BlockSuite rule like `input { display: flex; padding: 0; ... }` (confirmed to exist, unscoped, in two separate `@blocksuite/*` packages) silently overrides this app's own Tailwind-styled elements of the same tag, for every property it touches — no exotic bug, just cascade-layers doing exactly what the spec says.

**Fix pattern** (already used twice, both in `app/globals.css`): a targeted class + `!important` declarations that reclaim *every* property the offending global rule touches, not just the one that's visibly broken — `!important` is what lets a layered rule win back against an unlayered one. See `.page-canvas-title` (reclaims `display`/`width`/`margin`/`padding`/`font-size`/`line-height` against a leaking `input` rule) and `affine-menu .affine-menu-body` (reclaims list-height/scroll behavior) for the working examples.

If something looks subtly wrong — size, spacing, alignment, color — on an element that sits anywhere near the BlockSuite editor in the DOM, suspect this mechanism *first*, before assuming your own component's CSS is wrong.
