## Payload vs. raw `pg` boundary

Everything under `collections/*` goes through Payload's Local API (`getPayloadClient()` + `payload.find/create/update/delete`, always with `overrideAccess: true` — see the environment gotchas below for why). Never call Payload's REST or GraphQL endpoints from server code; the Local API is faster, type-safe against `payload-types.ts`, and is the only pattern used anywhere in this codebase today. If you ever need raw SQL against tables Payload doesn't own (the future `runs`/`run_messages`/`run_usage` per D5, or a one-off diagnostic read), open your own short-lived `pg.Pool` — see the shared-Supabase note below for why "short-lived and small" matters here specifically.

## Environment gotchas (verified against the live container and repo, not guessed)

- **Production build only, no hot reload.** Container `notionforge-app`, port 3000, entrypoint runs `npm install && npm run build && npm run start` on every start (confirmed via `docker inspect`). Source edits do not hot-reload — after any change, `docker restart notionforge-app` and wait ~1–2 minutes for the rebuild.
- **`node_modules` and `.next` are named Docker volumes, not part of the bind mount.** Confirmed via `docker inspect notionforge-app`: `notionforge-node-modules` → `/app/node_modules`, `notionforge-next-cache` → `/app/.next`; only the repo itself is bind-mounted to `/app`. A `npm install` on the host does not reach the container — the entrypoint's own `npm install` (which already runs on every restart) is what syncs a new dependency into the container's volume, so the standard "restart after any change" rule already covers dependency changes too; there's no separate step needed. If a rebuild ever crashes with a no-stack-trace error right after "Creating an optimized production build," suspect a stale `.next` volume first: `docker exec notionforge-app sh -c "rm -rf /app/.next/*"`, then restart.
- **`DATABASE_URI` points at a hosted Supabase project, not a local Postgres container** (confirmed — Pillar 1.3 will consolidate this onto one Postgres, not done yet). It's a small-tier instance with a real session-mode connection cap (~15, hit and confirmed live this session). Every teammate's dev server and every one-off script competes for that same small pool — keep any `pg.Pool` you open yourself small (`max: 2–3`) and close/let it exit promptly; don't leave an extra dev server idle-running longer than you need it.
- **DB safety rule**: never run a standalone script that calls `getPayloadClient()` against this shared DB. `payload.config.ts` has `push: false` (confirmed present) specifically to stop Payload's dev-mode schema-drift auto-push from silently dropping tables it doesn't recognize — this has already happened once this session to Better Auth's own `user`/`session`/`account`/`verification` tables, which live in the same Postgres database but outside Payload's schema awareness. Verify through the already-running container's Payload client instead of a fresh script. If a script genuinely needs its own Payload client, confirm schema is fully migrated first so there's no drift left for it to prompt about.
- **`tsc --noEmit` + `eslint` clean does not guarantee `npm run build` succeeds.** Next.js's SWC bundler is stricter than `tsc` for some syntax (this cost a real incident this session — a build-breaking syntax error passed both checks and looped the container's `unless-stopped` restart policy on a failing build for several minutes before being traced). Always run a real `npm run build` before calling a task done, not just the faster checks.
- **No browser access exists anywhere on this team.** Verification is API/DB/source-level: `curl` against live routes on the container, direct SQL reads via a short-lived `pg` connection, static code reading, isolated Node/`tsx` scripts for anything that needs real execution (e.g. a `happy-dom`-shimmed DOM for BlockSuite mount logic). Flag any pixel-level or visual-alignment claim as unconfirmed rather than asserting it looks right.

## The CSS-cascade-layers / BlockSuite global-CSS gotcha

BlockSuite's Lit components are deliberately "shadowless" (no shadow root, for editor performance) — their `static styles` get injected as **unlayered, unscoped** global `<style>` tags into `document.head`, not scoped to the component. Per the CSS cascade-layers spec, *any* unlayered rule beats *any* layered rule, regardless of specificity — and this app's own Tailwind utilities live inside Tailwind v4's `@layer utilities`. So a bare BlockSuite rule like `input { display: flex; padding: 0; ... }` (confirmed to exist, unscoped, in two separate `@blocksuite/*` packages) silently overrides this app's own Tailwind-styled elements of the same tag, for every property it touches — no exotic bug, just cascade-layers doing exactly what the spec says.

**Fix pattern** (already used twice, both in `app/globals.css`): a targeted class + `!important` declarations that reclaim *every* property the offending global rule touches, not just the one that's visibly broken — `!important` is what lets a layered rule win back against an unlayered one. See `.page-canvas-title` (reclaims `display`/`width`/`margin`/`padding`/`font-size`/`line-height` against a leaking `input` rule) and `affine-menu .affine-menu-body` (reclaims list-height/scroll behavior) for the working examples.

If something looks subtly wrong — size, spacing, alignment, color — on an element that sits anywhere near the BlockSuite editor in the DOM, suspect this mechanism *first*, before assuming your own component's CSS is wrong.

## Architecture decisions added in the current implementation

- **Approvals (P5.4)** are first-class Payload documents (`collections/Approvals.ts`) exposed by `app/api/approvals/route.ts` and coordinated by `lib/hermes/approval-helpers.ts`. The ACP `permissionCallback` seam in `lib/hermes/acp-client.ts` creates and waits on approvals for `ask`, selects an allow option for `auto`, and fails closed for `deny`/timeouts. Approval identity must always come from the authenticated session; never trust a client-supplied user id or header.
- **Payload migration operations:** when `payload migrate` encounters the known interactive development-drift prompt, do not confirm blindly. Handwrite the reviewed migration, apply it with a short-lived `pg.Pool` script (the established `scripts/apply-approvals-migration.ts` pattern), and insert the matching `payload_migrations` tracking row.
- **Inbox (P5.5)** lives at `app/(app)/workspace/[workspaceSlug]/inbox/page.tsx`; it combines pending approvals, failed runs, review-ready runs, and mention items using approval helpers, broker run reads, entity links, and the authenticated user. **Transcript (P5.6)** is the pure `lib/transcript/*` pipeline: ordered `RunEventEnvelope` input is redacted/projected into a timeline, paired into steps, grouped, and split into lanes/outcome; `scripts/test-transcript-pipeline.ts` is its repeatable fixture test.

- BlockSuite imports cross an app-wide module boundary: direct `@blocksuite/*` imports are confined to `lib/blocksuite-*.ts` wrappers (with `lib/blocksuite-doc.ts` as the server-side precedent). This prevents duplicate BlockSuite/Lit module graphs, which caused real `instanceof` and custom-element registration failures; new touchpoints must use a wrapper or add one.
- The daemon and Next.js processes are separate. The daemon's raw-`pg` broker owns `runs`, `run_messages`, and `run_usage`, while Payload/Yjs exist only in Next.js. A daemon-to-page write must call an authenticated Next API route; it must never attempt an in-process Payload or Yjs call.
- `RunEvent` is the single wire/storage contract in `lib/run-events.ts`. Its `page_write` variant confirms a persisted CRDT write (`status: 'committed'`), rather than expressing intent or a command; commands use a separate authenticated HTTP request/response path and are never encoded as RunEvents.

`lib/agent-page-writes.ts` is the scoped page-write primitive. `createRunSubtree()` creates a run-owned subtree and returns an opaque handle; `appendBlockToSubtree()` can append only supported block kinds below that handle. It must not become an arbitrary page mutation API. Both functions use `loadDocForWrite()` from `lib/blocksuite-doc.ts`.

`applyDocSync()` in `lib/blocksuite-doc.ts` hydrates the currently persisted Yjs state and merges the incoming update before persisting. It does not treat an incoming update as a replacement document; this CRDT merge is required because human and agent writers can overlap. The process boundary above still applies: a daemon invokes this through an authenticated Next route.

`lib/run-worktrees/manager.ts` creates each run branch as `agent/run/<runId>` and places its worktree under the configured run root. Teardown must explicitly choose whether uncommitted changes are discarded or preserved. Review delivery in `lib/run-worktrees/merge.ts` always creates a disposable integration worktree; it never merges into a live checkout directly. Git's default `receive.denyCurrentBranch=refuse` is a safety net, and the normal delivery path for a deployed checkout is `git pull --ff-only` (or its equivalent fetch plus fast-forward-only merge).

## Dispatcher/broker lessons (Pillar 4 wiring)

- **`app/api/dispatcher/tick/route.ts` runs inside the Next.js server process on purpose**, polled externally by `scripts/run-dispatcher-loop.ts` (`npm run dispatcher:loop`) — a plain HTTP client with zero Payload/`pg` imports of its own. Two real failure modes led here:
  - Embedding the poll loop directly in `instrumentation.ts` broke the dev server: Next bundles `instrumentation.ts` through webpack including an edge-runtime pass that can't resolve Payload's Node-only deps (e.g. `busboy` → `stream`), regardless of a runtime guard around the loop's own code. (`instrumentation.ts` today is back to just a startup log line and a process-wide `unhandledRejection` logger — see below for why that logger alone isn't a substitute for fixing a promise chain at its source.)
  - A standalone script importing `dispatchNextRun` — and therefore `getPayloadClient()` — directly opens a SECOND Postgres connection pool against the shared, connection-capped Supabase instance (see the connection-cap gotcha above), on top of the dev server's own pool and the broker's own pool. POSTing to the dev server's already-running `/api/dispatcher/tick` instead reuses its already-loaded env and its single cached Payload client — no new pool, no import-order hazard (an importing script's own `nextEnv.loadEnvConfig()` call always runs too late relative to `payload.config.ts` reading `DATABASE_URI` at top-level import time anyway, since ESM imports are hoisted).
  - `run-dispatcher-loop.ts` has no built-in pidfile/singleton guard — `.gitignore` reserves `.dispatcher-loop.pid`/`dispatcher-loop.log` for one, but "kill the previous poller before starting a new one" is an operator discipline today, not enforced in code. Multiple zombie pollers were left running simultaneously after repeated dev-server restarts this session, all writing to the same log file — the interleaved output looked like a much worse/flakier bug than the system actually had, including phantom "run claimed twice" noise. Always confirm the previous poller process is actually dead before starting a new one.

- **`agent.permissionMode` (`'ask'`/`'auto'`/`'deny'`) has to survive a five-link chain to actually take effect, and every link type-checks fine even if one silently drops the value**: the Payload field (`collections/Agents.ts`) → `lib/dispatcher/worker.ts`'s `executeRun` (passes `permissionMode: agent.permissionMode` into its `sendTurnWithIdentity` call) → `SendTurnWithIdentityOptions` (`lib/hermes/run-with-identity.ts`) → its inner call to `sendTurn` → `lib/hermes/acp-client.ts`'s `buildClientApp(permissionTimeoutMs, permissionMode)`. This broke for real once: `run-with-identity.ts` accepted `permissionMode` in its options *type* but never forwarded it into the actual `sendTurn(...)` call body, so every agent silently ran under `sendTurn`'s fail-closed default regardless of what was configured — `tsc`/`eslint` stayed clean throughout; only a live run with a real permission request caught it. Any new field added to `SendTurnOptions`/`SendTurnWithIdentityOptions` needs an explicit "does every call site along this chain actually forward it" check, not just a type addition.

- **`Promise.race([turnPromise, timeout])` must never re-await the promise it just raced against.** `sendTurn` (`lib/hermes/acp-client.ts`) wall-clock-caps a turn this way; the losing `turnPromise` is not guaranteed to ever settle on its own if the underlying child process died mid-turn — stdio streams closing is not the same as the ACP SDK detecting a protocol-level error, so `active.nextUpdate()` can simply never resolve. Re-awaiting the loser after the race gave up on it meant the wall-clock timeout could fire, push a `done: error` envelope, and `sendTurn` would *still* hang forever — and with it everything awaiting it, up through the dispatcher's HTTP route, blocking the shared single-claim-per-tick queue behind it. Attach `.catch(() => {})` without awaiting instead. Two related traps in the same function: `ReadableStream#cancel()`/`WritableStream#close()` always return a Promise, even when the stream can't actually be cancelled/closed cleanly (e.g. still locked by an active reader) — a bare `try/catch` around either call catches nothing, since neither throws *synchronously*; the real rejection only surfaces later as an unhandled promise rejection unless you also `.catch()` the promise each one returns. And `app.connectWith(...)` (the ACP SDK's own connection entry point) returns a promise that's independent of any `resolve()`/`reject()` called inside its callback — `void`-ing it discards the reference but attaches no rejection handler, so a connection-level failure (the SDK's own reader throwing "ACP connection closed" when the transport closes) is *also* an unhandled rejection unless caught separately. `instrumentation.ts`'s process-wide `unhandledRejection` logger stops these from hard-crashing the Next.js server process, but it doesn't unstick a hung request or reap a leaked child process — fixing each promise chain at its source is what actually matters; the logger is a last-resort net, not a fix.

- **Cross-check raw SQL INSERT column-count vs. placeholder-count vs. bound-params-array-length by hand whenever touching `lib/broker/`** — Postgres only catches a mismatch at query execution time, not statically, and template-string SQL isn't type-checked against its params array at all. This bit `enqueueRun` for real: a 9-column INSERT with a stray extra `$9` placeholder against an 8-element bound-params array would have failed *every single call* once real traffic hit it (`bind message supplies 8 parameters, but prepared statement requires 9`). Caught by actually running `scripts/test-broker.ts` against the live DB, not by `tsc` — a second bug in the same change (`rowToRun` never mapping a newly-required `prompt` field) *was* caught by `tsc`, which is the useful contrast: schema-shape bugs get caught for free, raw-SQL arity bugs don't.

All implementation changes happen in a dedicated `roadmap/*` branch/worktree and are handed to the lead for deliberate merge; do not push directly to `origin/main`. Do not run `npm install` or heavyweight builds in parallel worktrees when centralized verification is scheduled: the lead batches verification on `main`. Never modify a live checkout to test a branch, and never run destructive schema/data operations without explicit approval and a reviewed migration.

## Parallel worktree orchestration pattern (adopted this session)

`master` and `main` are kept identical except during an active batch: `master` is where parallel worktree branches merge as they land (eslint-only verification per branch, no `npm install`/`build` in the worktree — `node_modules` is shared into each worktree via an NTFS junction so eslint still works with zero install cost), and only after a whole batch is merged does one real `npm install && npm run build` run once, on `master`, to catch what eslint can't (see the four real bugs this caught below). Once that build is green, `main` is fast-forwarded to `master` and both are pushed. Do not run per-worktree builds — that defeats the point of batching.

**Confirmed live 2026-09-02, batch 1 (7 parallel branches merged, eslint-clean individually, build run once on `master` after all merges):** the batched build caught four real bugs that seven clean per-branch eslint passes did not, because they were only visible once the branches' changes coexisted:
1. Two branches independently created `app/api/runs/[runId]/...` and the pre-existing `app/api/runs/[id]/...` — Next.js hard-errors on two different dynamic-segment names at the same route level. Not visible until both existed in the same tree.
2. `RunEvent`'s `page_write.kind` stayed `'heading' | 'paragraph'` in one branch while `lib/agent-page-writes.ts`'s `BlockSpec.kind` was independently widened to add `'list' | 'code'` in a different branch — a real type mismatch only `tsc` (via `next build`) catches, not per-file eslint.
3. A UI branch's `agent-capabilities.tsx` declared its own narrower local `Agent` type instead of importing the fuller one already exported from `agent-editor.tsx`, breaking a callback's assignability once both files coexisted.
4. `lib/dispatcher/worker.ts`'s `inFlightRuns` map assumed `Promise<void>`, but the real resolved value of `executeRun(...)` leaked through its `.catch()` chain — caught by `tsc`, not eslint.

**Lesson, reinforcing the existing "tsc/eslint clean does not guarantee build succeeds" rule above:** this is *worse* with parallel branches than with one branch, because eslint runs per-file and per-branch — it cannot see a type or route conflict that only exists once two branches' independent changes are combined. The single batched build after merging is not optional; it is the only check that catches this class of bug at all.

Overflow parallel capacity beyond Claude subagents: `opencode` and `hermes` are both on `PATH` and usable via `opencode run "<prompt>" --dir <worktree> --model <model> --auto` (backgrounded via the shell). `opencode run` with `--auto` (auto-approve permissions) works well for a self-contained, well-scoped UI build task in its own worktree, same eslint-only/single-commit discipline as a Claude subagent. No `aion`/`aionui` binary was found on `PATH` this session despite an earlier HANDOFF.md note referencing it — don't assume it's available without checking first.

**When several parallel branches will edit the same shared file** (a root layout, a shell component multiple features mount into), don't let every branch touch it — one shared-file edit per branch merges fine via `git merge --no-ff` (ort strategy resolves same-file-different-region edits automatically, confirmed across two batches now, up to three branches touching `components/sidebar/sidebar.tsx` simultaneously with zero conflicts), but the *wiring* of new providers/components into that shared file (e.g. `app/(app)/workspace/[workspaceSlug]/layout.tsx` mounting a new context provider) is safest done once, by the lead, after all branches land — have each branch build its piece as a self-contained, exported component and state its exact one-line integration snippet in its final report, rather than have multiple branches race to edit the mount point themselves.
